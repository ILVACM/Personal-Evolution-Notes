## 2. 现有扫描/遍历机制现状

**结论：v2.0 已有一个"要求遍历"的种子机制（§2.2），但极不完整基本靠启发式，完全没有强制的全量+穷举协议。**

- **是否要求遍历**：是（部分）。§2.2 "扫描项目根目录及子目录…**递归扫描全部目录**"，且给出 7 个问题的"扫描完成判定标准"。§2.1 能力项含"目录树遍历与文件列表获取能力"。
- **在哪里、怎么要求**：
  - §2.2 现状扫描（是否已存在 AGENTS.md/docs/knowledge/README、散落.md、`governance: instance` 疑似实例、项目结构技术栈规模）。
  - §10.1 角色表 **Scanner Agent**："现状扫描与评估"，加载"**仅目录结构 + 各文件首 20 行（或标题/摘要）**"。
  - §10.2 **Step 1 前置决策**：完成第 2 章流程（2.1→2.2→2.3→2.4→2.5），即扫描结果直接喂给决策报告。
- **扫描范围**：偏 `.md` / 文档类与结构类信息，未穷举代码与非 Markdown 规约文件（YAML/TOML/JSON、Makefile、Dockerfile 等不在 §2.2 显式列范围内；仅 2.6.1 校验对象涉及配置文件）。
- **无深度限制要求**：§2.2 未设递归深度上限要求，也未禁止截断。
- **无隐藏目录/文件要求**：§2.2 未显式提及 dotfiles/dotdirs（.github/、.vscode/、.config/、.env 等）。
- **无符号链接处理**：全文未见。
- **无 monorepo 处理**：仅 2.6.1 提到"入口文件及其直接导入/引用的模块"，未做多子项目单元划分。
- **无排除项列表**：§2.2 未定义应排除的构建产物目录（node_modules/dist/build/.git 等）。
- **无分片扫描**：无文件数/深度阈值触发分片。
- **无断点续传**：无中断恢复机制；10.1 单 Agent 降级只有"分段读取每段 ≤250 行"，是针对单篇文档读取，非分片续传。
- **无扫描完整性证明/门禁**：§2.2 有"7 个问题均能给出答案"作为完成判据，但无"文件系统工具计数 vs 清单计数误差=0"式可验证闭环，无 COMPLETE/INCOMPLETE 状态门禁。

## 3. 现有分析机制现状

**结论：v2.0 的"分析"分散在 §2.2、§2.6、§10.2 三处，均不是"基于完整扫描清单"的系统性分析，无正式候选清单概念。**

- **"现状分析"工作方式**：
  - §2.2 现状扫描：分析结论直接写入决策报告的『现状』字段，判定 A/B/C/D（§2.3）。
  - §2.6 规约真实性校验与自适应推测：2.6.1 一致性校验、2.6.2 有限推测（允许/禁止范围）、2.6.3 多 Agent 并行（_temp/verify-*.md / infer-*.md）、2.6.4 可信度五级标签。
  - §10.2 Step 2 校验与推测前置（执行 2.6 全流程）、Step 3 既有文档三层分流判定。
- **输入是否为完整扫描**：否。§2.6.1 校验对象是"目录结构、入口文件、配置文件、入口的直接依赖模块、CI/CD"，范围被收窄到"**以入口文件所在目录为范围**"（无法判定依赖关系时）；Scanner Agent 只读"各文件首 20 行"。因此输入来自切片式/启发式信息，非穷举清单。
- **涉及文件类型**：校验侧覆盖配置文件（package.json/pyproject.toml/go.mod、Scripts/Makefile/Dockerfile）、CI/CD；分析侧主要围绕 `.md`/文档类。未系统覆盖全部实际存在的文件类型分类。
- **有无候选清单概念**：无正式的"潜在规约文档候选清单"。最接近的是：§2.2 "是否存在携带 `governance: instance` 标识或疑似实例文档…散布于何处"、§10.2 Step 3 "将既有文档分为四类"（约束/通用规范/实例/不管辖）。这是**事后分流**，缺**事前穷举登记候选 + 逐候选提取 7 项**的机制。
