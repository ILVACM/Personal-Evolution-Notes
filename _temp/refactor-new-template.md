# 任务：确保项目三层 Agent 规约体系达标（自适应执行）

## 1. 任务概述与目标

你的任务是确保本项目仓库具备一套符合本提示词下述标准的 **三层 Agent 规约体系（约束层 + 知识层 + 实例注册）**。这不意味着必须从零创建——你需要先评估现状，再决定执行路径。

任务目标：

1. 产出一套三层 Agent 规约体系：约束层（`docs/`）+ 知识层（`knowledge/`）+ 实例层（散布于项目自然归属位置、经 `knowledge/Instances-INDEX.md` 统一注册）；
2. 体系必须**自包含**：建成后，任何 Agent 无需额外上下文，即可从 `AGENTS.md` 路由开始工作；
3. 先评估现状，按情况 A/B/C/D（见 2.3）自适应选择执行路径；
4. 无论起点如何，结束时体系必须完全符合本提示词第 3~9 章定义的标准，且第 11 章校验清单全项通过。

## 2. 前置条件与假设

本任务的执行遵循严格的"先决策再操作"原则。在动手修改任何文件之前，你必须完成 2.1~2.5 的评估与决策；在创建/改写任何正式文档前，必须完成 2.6 的校验与推测。

### 2.1 权限与能力确认

执行前请确认你已具备以下能力，若任何一项缺失则立即报告而非静默跳过：

- 文件与目录的读取、创建、写入、修改、删除、移动权限
- 目录树遍历与文件列表获取能力
- 若项目依赖 MCP（Model Context Protocol）服务或特定 Skills（如 Git 操作等），以实际调用一次最小操作验证就绪（如成功执行一次只读命令 `git status`）；调用失败即视为缺失，按上一条『立即报告』处理
- 多 Agent 协作能力检测：检测当前环境是否支持多 Agent 协作（子 Agent 派发 / Worker / Task Delegation 等）
  报告后停止一切文件修改操作，等待用户确认后再继续；若仅多 Agent 协作能力缺失，无需等待，直接按 10.1「构建协作方式二：单 Agent（降级）」执行，并在决策报告中注明。

若权限完备，直接开始执行。

### 2.2 现状扫描

扫描项目根目录及子目录，重点关注：
递归扫描全部目录；扫描完成的判定标准为下述 7 个问题均能给出答案（因权限或读取失败无法回答的，记为『无法回答 + 原因』）。扫描结论直接写入决策报告的『现状』字段。

- 是否已存在 `AGENTS.md`？内容完整度如何？
- 是否已存在 `docs/` 目录？内含哪些文件？是否有索引？
- 是否已存在 `knowledge/` 目录？内含哪些通用规范与索引？
- 是否已存在 `README.md`？内容覆盖度如何？
- 是否存在其他散落的文档（如 `CONTRIBUTING.md`、`wiki/`、`guides/`、零散的 `.md` 文件等）？
- 是否存在携带 `governance: instance` 标识或疑似实例文档（部署文档、配置说明、实施方案、特定项目 README 等）？散布于何处？
- 项目本身的结构、技术栈、规模如何？

### 2.3 执行模式判定

根据扫描结果，判定属于以下哪种情况，并选择对应路径：

| 情况 | 判定标准 | 执行路径 |
|------|----------|----------|
| A. 从零新建 | 不存在 `AGENTS.md`，不存在 `docs/` 目录，无有效规约体系 | 按本提示词完整创建三层规约体系 |
| B. 局部补全 | 存在部分文档（如有 `README.md` 但无 `AGENTS.md`，或有零散 `.md` 但无结构化 `docs/`，或有零散通用规范但无 `knowledge/` 结构） | 保留已有内容，补建缺失部分，整合散落文档**按三层分流**（见 10.2 Step 3） |
| C. 重构规范化 | 已有规约类文档（`AGENTS.md`、`docs/`、`knowledge/` 下的 .md 文件）合计 ≥2 篇且总行数 ≥100 行，但结构/格式/索引不符合本提示词标准 | 保留核心内容，重组结构，补建索引，统一格式，整合散落文档**按三层分流**（见 10.2 Step 3） |
| D. 校验修正 | 已有完整规约且基本符合本提示词标准，仅存在不影响 Agent 解析与执行的问题（限：格式不一致、索引个别条目缺失、个别标签过时三类；不含板块缺失与路由失效） | 仅修正不一致处，不做大改动 |

### 2.4 关键保护原则

无论哪种执行路径，以下规则不可违反：

- ❌ 禁止未经分析直接删除或归档任何已有文档内容
- ❌ 禁止假设已有文档"无用"而跳过不读
- ✅ 已有文档中可用的内容必须保留，可以移动、重组、改写格式，但信息本身不得丢失
- ✅ 若某份已有文档的内容确实与当前项目不符（如过时、错误），必须标注 `[已过时-待确认]` 而非直接删除，并在汇报中说明
- ✅ 若需合并多份文档，合并后原文件可删除，但必须确保所有内容已被完整迁移
  『完整迁移』以逐项比对判定：原文件的标题与关键信息点须全部出现在合并后的目标文件中，或已标注 `[已过时-待确认]`；比对通过并记入汇报后方可删除原文件。
- ✅ 重构时优先移动和重命名，而非删除后重写
- ✅ 对识别为实例层的既有文档，默认**原地保留**，仅允许新增头部元信息区与完成注册登记，正文按第 6 章规则整理，信息不得丢失
- ❌ 本任务仅允许新增/修改/移动/删除规约类文档（`AGENTS.md`、`README.md`、`docs/`、`knowledge/`、实例文档的元信息区与注册登记、`_temp/`）；禁止修改任何代码、配置文件、依赖清单与 CI/CD 脚本

### 2.5 决策报告

在动手操作前，向我输出简要决策报告：无需等待确认，输出后立即按下方两条对应路径继续执行；若用户另行指示，以用户指示为准。

```
📋 [决策报告]
- 现状：简述已有文档情况
- 判定：情况 A / B / C / D
- 执行路径：简述将做什么（保留什么、新建什么、重组什么）
- 协作模式：多 Agent / 单 Agent
- 风险点：（如有）可能的内容冲突或不确定项
```

- 若判定为情况 D（仅校验修正），报告后仍须先执行 2.6 一致性校验（范围限定为已有规约文档与实际产物），通过后再进入第 11 章校验清单与 8.4 校验流程，不执行第 3~7 章与 10.2 的新建与重组操作。
- 若判定为 A / B / C，报告后继续执行后续章节。

### 2.6 规约真实性校验与自适应推测（含可信度五级标签）

⚠️ 本节为强制执行环节。无论 README 或现有文档看起来多么完整可信，都必须执行一致性校验；当文档缺失或不完整时，必须在受限范围内进行自适应推测（边界条件见 2.6.2）。此环节是规约可信度的基石。

#### 2.6.1 文档与实际内容一致性校验

Agent 读取任何文档（README/docs/注释）后，不得无条件采信，必须与项目实际产物交叉验证。

**校验对象：** 目录结构、入口文件、配置文件（package.json/pyproject.toml/go.mod 等）、入口文件及其直接导入/引用的模块（无法判定依赖关系时，以入口文件所在目录为范围）、CI/CD（持续集成/持续部署）配置。

**校验维度：**

- 技术栈声明 vs 实际依赖清单
- 目录结构描述 vs 真实文件系统
- 启动/构建命令 vs Scripts/Makefile/Dockerfile
- 架构描述 vs 代码模块划分

**偏差处理：** 发现不一致时，以实际代码/配置为准，并在输出中明确标注 `[存在差异]`，同时记录差异详情至 `_temp/verify-discrepancies.md`。
若实际产物之间相互矛盾，以运行时实际生效者为准；无法判定生效关系时，将矛盾各方均标注 `[存在差异]`，矛盾对记入 `_temp/verify-discrepancies.md` 并列入待人工确认清单。

**不可跳过：** 即使文档声称"最新"，也必须完成至少一轮 『文档声明 → 实际产物』逐项比对：比对须以实际读取配置文件、目录列表、脚本为准（不得仅凭文档文本判断），逐项比对结果须写入 `_temp/verify-*.md`。

#### 2.6.2 文档缺失时的自适应有限推测

当关键信息无文档说明或说明不完整时，允许基于有限线索进行推测，但必须严格遵守以下边界：
此处『关键信息』指按第 3~9 章构建规约所必需的信息：项目用途、技术栈、运行环境与部署目标、目录结构、入口与构建命令。

**允许推测的范围（仅限）：**

- 项目核心功能/用途（What it does）
- 运行环境与部署目标（Where it runs）
- 技术栈与框架版本（Tech stack）

**禁止推测的范围（红线）：**

- ❌ 业务逻辑细节、算法实现原理
- ❌ 未来规划、Roadmap
- ❌ 团队分工、负责人信息
- ❌ 未经验证的性能指标、安全声明

**推测依据：** 仅可基于目录命名规范、代码注释、依赖清单、配置文件字段、Git 提交信息等客观痕迹。

**标注要求：** 所有推测内容必须显式标注 `[推测]` 或 `[推断]`，并注明依据来源（如"基于 package.json dependencies 推断"）。
若项目无任何代码与文档线索，仍须创建 `AGENTS.md`、`docs/INDEX.md`、`docs/agent-execution-mode.md`、`knowledge/INDEX.md`、`knowledge/Instances-INDEX.md` 骨架，信息点全部标注 `[待补充]`，并在汇报中输出待人工补充清单。

#### 2.6.3 多 Agent 并行校验与推测执行规范

为应对大仓库上下文过长风险，校验和推测环节必须采用多 Agent 并行模式（若环境支持）：

- **任务拆分：** Orchestrator（主控）将校验/推测任务按模块/目录拆分为独立子任务。
- **临时文件机制：** 每个子 Agent 将结果写入 `_temp/verify-*.md`（校验类）或 `_temp/infer-*.md`（推测类）（如 `_temp/verify-backend-deps.md`、`_temp/infer-tech-stack.md`），禁止直接在内存中返回长文本。
  写入前若已存在同名文件，直接覆盖（以本次结果为准）；任务结束后保留 `_temp/` 目录供审计追溯，不做清理。
  Orchestrator 分派任务时为每个子任务指定唯一文件名（`verify-<模块名>.md` / `infer-<主题名>.md`）；禁止两个子 Agent 写入同一文件。
- **汇总机制：** Orchestrator（主控）仅读取 `_temp/` 下的结果文件进行汇总，生成最终的可信度分层报告。
- **降级策略：** 若不支持多 Agent，则串行执行，但仍需将中间结果写入 `_temp/` 以保持流程一致性和可追溯性。

#### 2.6.4 可信度分层输出标准

在项目背景、技术栈、架构概述、运行环境、部署目标五类段落，以及决策报告与校验报告中的结论性语句中，必须使用以下标签之一作为前缀，便于人工审阅时快速判断复核力度：

| 标签 | 含义 | 人工复核建议 |
|------|------|-------------|
| `[已校验一致]` | 文档描述与实际代码/配置完全吻合 | 低优先级抽查 |
| `[存在差异]` | 文档与实际不一致，已按实际修正 | 高优先级复核 |
| `[推测]` | 无直接文档，基于单一客观线索推测得出 | 中优先级确认 |
| `[推断]` | 基于多处间接证据综合推断得出（线索数量 ≥ 2 且相互印证） | 中优先级确认 |
| `[待补充]` | 无任何线索，无法推测 | 需人工介入 |

遇 `[待补充]` 项时：不中断整体流程，将该项写入 `_temp/verify-*.md` 的『待人工介入』专节，继续完成其余工作；最终汇报中单列待介入清单，由用户决定补充方式。

## 3. 规约体系结构总览

无论执行路径如何，最终必须达到以下标准状态——三层 Agent 规约体系：

```text
AGENTS.md（总纲 · 唯一第一入口 · 最高权威）
    │
    ├──► docs/（约束层）
    │       ├ INDEX.md
    │       └ 规约细则...
    │
    ├──► knowledge/（知识层 + 实例注册）
    │       ├ INDEX.md（知识层总索引）
    │       ├ Instances-INDEX.md（实例层注册表）
    │       └ 通用规范文档...
    │
    └──► 实例文档（散布于项目各自然归属位置）
```

配套说明：

- `AGENTS.md` 为规约总纲、唯一第一入口，是体系内最高权威；
- `docs/` 为约束层，存放规约细则；`knowledge/` 为知识层，存放通用规范文档并承载实例注册表；实例文档不集中存放，散布于项目各自然归属位置；
- `README.md` 与 `_temp/` 为体系外配套：`README.md` 是面向人类的项目关键信息展示窗口，无约束力；`_temp/` 为校验与推测中间产物目录，供审计追溯，不做清理。

三层定义与管辖范围见第 4 章；路由设计见第 5 章；管辖范围边界见第 7 章。

## 4. 三层定义与管辖范围

### 4.1 约束层（docs/）

| 属性 | 定义 |
|------|------|
| 定位 | Agent 行为规则的唯一权威来源 |
| 内容 | 编码规范、架构约定、工作流约束、多 Agent 协作规范、运行方式判定标准、全局校验机制 |
| 性质 | 规定性（Prescriptive） |
| 约束力 | `[约束]`——违反即为执行错误 |
| 变更频率 | 低 |
| 维护者 | 规约管理者（人） |
| 路由职责 | `INDEX.md` 作为约束层总路由，向下仅给出知识层入口指针，不列知识层或实例层明细 |

### 4.2 知识层（knowledge/）

| 属性 | 定义 |
|------|------|
| 定位 | 通用规范与参考知识的集合，是实例层的"模具" |
| 内容 | 环境规范（服务器参数、网络约束等）、技术选型指南、通用部署规范、安全基线、性能标准等 |
| 性质 | 描述性（Descriptive） |
| 约束力 | `[参考]`——Agent 应当遵守；与约束层冲突时以约束层为准 |
| 变更频率 | 中 |
| 维护者 | 领域负责人（人） |
| 路由职责 | `INDEX.md` 按领域分类，每条规范标注其下游实例清单（含物理路径） |

### 4.3 实例层（散布 + Instances-INDEX.md 注册）

| 属性 | 定义 |
|------|------|
| 定位 | 具体项目的执行文档，是知识层规范的"铸件" |
| 内容 | 具体部署文档、配置说明、实施方案、特定项目 README 等 |
| 性质 | 执行性（Operational）——自包含的完整操作指令 |
| 约束力 | `[自包含指令]`——文档本身即为完整执行依据 |
| 变更频率 | 高 |
| 维护者 | 项目实施者（人或 Agent） |
| 物理位置 | **不集中存放**，置于项目自然归属位置 |
| 身份判定 | 文档头部元信息区包含 `governance: instance` 字段 |
| 注册方式 | 在 `knowledge/Instances-INDEX.md` 中登记路径与继承关系 |

⚠️ 实例文档不集中存放；不存在独立的 `instances/` 目录；实例注册表为 `knowledge/Instances-INDEX.md`。

## 5. 路由设计

### 5.1 AGENTS.md 总纲内容要求

必须包含以下板块：

1. **全局行为约束：** Agent 通用规则；声明本文件为规约总纲、最高权威
2. **运行方式判定规则（强制首项）：**
   - 显式声明：**"Agent 接到任何任务后，在执行实际操作之前，必须先确定本次任务的运行方式。"**
   - 路由路径：`→ docs/agent-execution-mode.md`
   - 标准流程：`AGENTS.md → docs/agent-execution-mode.md → 确定模式 → 开始执行`
   - 此规则为硬性前置条件，不可跳过、不可延后
3. **规约路由指引（双分支完整路由声明，必须写入）：**
   - 分支一（约束层链路）：`AGENTS.md → docs/INDEX.md → 约束层细则`
   - 分支二（知识层-实例层链路）：`AGENTS.md → knowledge/INDEX.md → 通用规范 → Instances-INDEX.md → 实例文档`
   - 回溯说明：实例文档元信息区 `inherits_from` 字段仅供回溯维护使用，执行时仅阅读正文（见 6.2、6.4）
   - **约束力层级声明（必须写入）：** `AGENTS.md` ＞ `docs/` ＞ `knowledge/` ＞ 实例文档；冲突时上层覆盖下层（详见第 12 章）
   - 渐进式加载，禁止全量读取
4. **多 Agent 协作规范（运行期）：**
   - 本项目支持多 Agent 协作
   - 最小上下文原则
   - 任务传递仅含指令+路径
   - 子 Agent 仅返回摘要，校验/推测结果写入 `_temp/`
   - 具体模式选择标准见 `docs/agent-execution-mode.md`
5. **全局更新校验机制（完整写入，见 8.4）**
6. **文档变更操作规范：** 任何变更后必须执行全局校验
7. **可信度标签使用说明：**
   - 列出所有可用标签及其含义
   - 要求在关键输出中强制使用

### 5.2 docs/INDEX.md 内容要求

**此文档为约束层总路由，规约体系的必建交付物，构建时必须生成，不可省略。** 职责两条：

- **约束层内文档清单与路由：** 文档清单表，每条含文件路径、标题、一句话摘要、标签/分类、最后更新日期、可信度状态
- **向下仅给出知识层入口指针：** 以一行指向 `knowledge/INDEX.md`，**不列知识层或实例层文档明细**

补充要求：

- `docs/agent-execution-mode.md` 必须作为索引清单第 1 条；任何顺序调整不得使其排在第 3 条之后。
- 路由说明：Agent 如何按关键词/主题定位目标文档（关键词/主题路由仅限约束层内部适用）
- 维护规则：约束层文件增删改时同步更新索引，一一对应无遗漏

### 5.3 knowledge/INDEX.md 内容要求

**此文档为知识层总索引，规约体系的必建交付物，构建时必须生成，不可省略。** 内容必须包含：

- 按领域分类列出全部通用规范
- 每条规范标注其下游实例清单（含实例物理路径）
- 每条清单记录含：文件路径、标题、一句话摘要、最后更新日期、可信度状态
- 维护规则：通用规范增删改、实例注册变化时同步更新，且与 `knowledge/Instances-INDEX.md` 登记内容保持一致

### 5.4 knowledge/Instances-INDEX.md 内容要求

**此文档为实例层注册表，规约体系的必建交付物，构建时必须生成，不可省略。** 内容必须包含：

- 每条实例登记：实例文档物理路径、所属项目、继承规范（`knowledge/` 路径）、状态（active / deprecated）
- 维护规则：新增/移动/删除实例时同步更新（联动 8.2 生命周期操作）
- 文件内明确声明：本文件是**唯一**的实例注册表，不存在独立的 `instances/` 目录

### 5.5 必建文档：docs/agent-execution-mode.md 内容规范

此文档为规约体系的标准交付物，构建时必须生成，不可省略。内容必须包含：

**① 模式定义（至少涵盖以下四种）：**

| 模式 | 名称 | 适用条件 | 执行方式 |
|------|------|----------|----------|
| A | 单 Agent 直接执行 | 任务范围小（参考阈值：涉及文件 ≤5 个且模块 ≤2 个，可按项目调整）、上下文可控、无需拆分 | 一个 Agent 顺序完成全部操作 |
| B | 多 Agent 协作执行 | 任务复杂（参考阈值：涉及文件 >5 个或模块 >2 个）、涉及多模块/多文件、环境支持子 Agent 派发 | Orchestrator 拆分任务，多 Agent 并行/串行协作 |
| C | 单 Agent 降级执行 | 环境不支持多 Agent，但任务本身复杂度较高 | 单 Agent 分步骤串行执行，每步仅加载当前步骤所需上下文 |
| D | 混合模式 | 环境仅支持部分协作能力（如可派发子 Agent 但不支持并行），需按环节混合串并行，且与模式 B 互斥：环境完整支持协作时不得选用本模式 | 按环节混合使用，明确标注哪些步骤并行、哪些串行 |

**② 模式选择判断标准：**

Agent 在读取本文档后，必须依据以下维度进行判定：

- **任务复杂度：** 涉及文件数量、模块数量、操作类型（读/写/创建/删除）
- **上下文规模：** 预计需要加载的文档/代码总量是否超出单次上下文窗口
- **环境能力：** 当前 Agent 环境是否支持子 Agent 派发（检测方式见下）
- **任务耦合度：** 各子任务之间是否存在强依赖（有则倾向串行）

**③ 环境能力检测方法：**

必须提供至少一条可直接执行的检测步骤，每条步骤须包含：执行动作、成功的表现、失败的表现（下方示例可直接采用或等价替换：）

- 尝试派发一个最小子任务（如"读取某文件第一行并返回"）
- 检测是否存在子 Agent 派发（Task Delegation / Worker / Sub-Agent）等机制
- 若原判定为模式 B 或模式 D 且检测失败，自动降级为模式 C；若原判定为模式 A，维持模式 A

**④ 降级策略：**

- 模式 B → 模式 C、模式 D → 模式 C（或模式 A）的降级条件与切换流程
- 降级后如何保持流程一致性（中间结果仍写入 `_temp/`）
- 降级后如何在输出中注明实际执行模式

**⑤ 输出声明要求：**

Agent 确定运行方式后，必须在任务开始时输出（本条款自规约体系建成后的任务起生效，本次构建任务不适用）：

```
🔧 [运行方式]
- 选择模式：A / B / C / D
- 判定依据：（简述）
- 环境能力：支持多Agent / 不支持多Agent
- 降级情况：无 / 已从 B 降级至 C / 已从 D 降级至 C 或 A
```

路由链路：

```text
    │       └── 指针：knowledge/INDEX.md
```

## 6. 继承与扩展规则（知识层 → 实例层）

### 6.1 继承规则

| 规则 | 说明 |
|------|------|
| 只能继承和扩展 | 实例文档必须包含所继承知识层规范的所有相关约束 |
| 不能覆写或矛盾 | 不得出现与所继承知识层规范相矛盾的表述 |
| 偏离需豁免 | 先在知识层新增豁免条款（编号），实例在 `overrides` 字段引用（见 6.3） |
| 自包含原则 | 正文中不得出现"详见知识层 XX"等跳转指令，所有信息在文档内完整呈现（见 6.2） |
| 元信息与正文分离 | 继承来源等置于文档头部声明区，执行时仅阅读正文（见 6.4） |

### 6.2 自包含原则

- 实例文档正文中不得出现"详见知识层 XX"等跳转指令
- 所有执行所需信息必须在文档内完整呈现
- 元信息区的 `inherits_from` 仅供回溯维护使用，执行时仅阅读正文

### 6.3 豁免机制

实例文档需要偏离所继承的知识层规范时：

1. 先在对应知识层规范中新增豁免条款并编号
2. 实例文档元信息区 `overrides` 字段引用该豁免条款编号
3. ❌ 禁止未经豁免的偏离——未经豁免的偏离即视为与所继承规范矛盾，违反 6.1

### 6.4 实例文档元信息区模板（含元信息与正文分离）

实例文档必须在头部包含元信息区。元信息与正文分离：继承来源等元信息置于文档头部声明区，执行时仅阅读正文。

```yaml
---
title: <文档标题>
version: <版本号>
last_updated: <日期>
governance: instance
inherits_from:
  - knowledge/<规范文件名>.md
overrides: none | <豁免条款编号>
status: active | deprecated
---
```

字段说明：

| 字段 | 说明 |
|------|------|
| `title` | 文档标题 |
| `version` | 版本号 |
| `last_updated` | 最后更新日期 |
| `governance: instance` | 实例层身份标识；头部含此字段即属实例层管辖（见 8.3） |
| `inherits_from` | 所继承的知识层规范路径列表 |
| `overrides` | `none` 或所引用的豁免条款编号（见 6.3） |
| `status` | `active` / `deprecated` |

## 7. 管辖范围边界

| 属于规约体系管辖 | 不属于规约体系管辖 |
|------------------|-------------------|
| `AGENTS.md` | 项目源代码 |
| `docs/` 下所有规约文件 | 构建产物（dist/、build/） |
| `knowledge/` 下所有通用规范文档 | 运行时数据、日志 |
| `knowledge/Instances-INDEX.md` | 第三方依赖源码 |

特别声明：

1. 实例文档**不集中存放**，置于项目各自然归属位置；
2. `knowledge/` 目录下**仅有** INDEX.md、Instances-INDEX.md 和通用规范文档，**不存放实例文档本体**；
3. `instances/` 目录**不存在**，实例注册表为 `knowledge/Instances-INDEX.md`；
4. `_temp/` 为校验与推测中间产物目录，属体系外配套，供审计追溯，不做清理。

- 任何 Markdown 文档头部含 `governance: instance` 即视为实例层管辖

- 未注册但携带标识的文档，Agent 应报告注册缺失

### 8.4 全局更新校验机制（必须完整写入 AGENTS.md）

**触发条件：** 任何规约文档变更完成后（新建、删除、修改、移动、重命名），无论之前是否校验过、无论提示词是否要求，必须执行以下三步。

**多 Agent 模式下：** 由 Orchestrator 调度 Auditor Agent 分步执行，每步仅加载该步所需文件，禁止合并。

#### Step 1 — AGENTS.md 自洽性审计

- 仅加载 `AGENTS.md`
- 检查：
  - 逻辑自洽、各板块无矛盾
  - 双分支路由均声明且路径有效（分支一指向 `docs/INDEX.md`、`docs/agent-execution-mode.md`；分支二指向 `knowledge/INDEX.md`、`knowledge/Instances-INDEX.md`）
  - **运行方式判定规则板块存在且路由路径有效**
  - 校验机制完整
  - 可信度标签一节包含 2.6.4 全部 5 个标签及含义，且 AGENTS.md 其余位置出现的标签拼写与用法与其一致
- 有问题则修正后重新审计
- 重新审计最多 3 轮；仍不通过的，输出未通过项清单与原因，标注 `[待补充]`，终止本轮校验并在最终汇报中置顶说明。

#### Step 2 — 三索引一致性校验

- 仅加载：`docs/INDEX.md` + `docs/` 目录文件列表；`knowledge/INDEX.md` + `knowledge/` 目录文件列表；`knowledge/Instances-INDEX.md` + 全库携带 `governance: instance` 的文档清单
- 比对：
  - `docs/INDEX.md` ↔ `docs/` 实际文件：无幽灵条目、无遗漏；`docs/agent-execution-mode.md` 已列入索引且路径正确；每条记录的路径在 `docs/` 下实际存在；标题与文件一级标题一致；摘要不超过一句话；可信度状态为五个标签之一且已填写
  - `knowledge/INDEX.md` ↔ `knowledge/` 通用规范文件 + 每条下游实例清单：一一对应，无幽灵条目、无遗漏
  - `knowledge/Instances-INDEX.md` ↔ 全库携带 `governance: instance` 的文档：一一对应，无幽灵条目、无遗漏，登记的每条实例路径实际存在
- 不一致则修正

#### Step 3 — README.md 同步更新

- 仅加载 `README.md` + 相关文档摘要（不读全文）
- 确保信息准确、无约束条款、关键信息带可信度标签
- 有变化则更新

```

- docs/INDEX.md：N 篇文档，索引与实际文件一一对应，docs/agent-execution-mode.md 已收录，可信度状态已填写
- knowledge/INDEX.md：N 篇通用规范，下游实例清单与实际一致
- knowledge/Instances-INDEX.md：M 个实例，注册与全库实例文档一一对应
- 实例文档：元信息区完整，正文无跳转指令
- README.md：已同步，信息准确，关键信息带标签

- 协作模式：多 Agent 协作 / 单 Agent 降级
```

## 9. 核心设计原则

| 原则 | 体现 |
|------|------|
| 唯一入口 | Agent 一切路由从 AGENTS.md 开始 |
| 规定与描述分离 | 约束层管"怎么做"，知识层管"是什么" |
| 模具与铸件分离 | 知识层是通用规范，实例层是具体实现 |
| 实例自包含 | 实例文档正文独立可用 |
| 物理位置自由，逻辑注册统一 | 实例文档放自然位置，通过 Instances-INDEX.md 统一注册 |
| 上层覆盖下层 | 约束力严格按层级 |
| 低层变更不污染高层 | 实例层高频变更不影响约束层 |

## 10. 执行步骤

### 10.1 构建协作方式（多 Agent 优先 / 单 Agent 降级）

> ⚠️ **本节定位：** 本节仅指导「构建规约体系」这一任务本身的执行方式，即施工队如何协作把房子盖好。它**不是**规约体系的交付内容。规约建成后，Agent 日常工作的运行方式由 `docs/agent-execution-mode.md` 规范（内容规范见 5.5，体系定位见第 3、4 章）。本节对 10.2 全部步骤适用。

#### 构建协作方式一：多 Agent 协作（优先）

**触发条件：** 当前环境支持子 Agent 派发或任务委托机制。

**核心原则：** 每个子 Agent 仅加载完成任务所需的最小上下文，禁止任何 Agent 一次性加载整个规约。

**推荐分工架构（可根据实际协作能力自适应调整）：**

调整仅限合并角色或由同一 Agent 兼任多角色；扫描、校验、写入、索引、审计五类职责不得省略，合并情况须在决策报告中注明。

| 角色 | 职责 | 加载的上下文 |
|------|------|-------------|
| Orchestrator（主控） | 任务拆解、分发、汇总、校验调度 | 仅 `AGENTS.md` + 本提示词 + 决策报告 |
| Scanner Agent | 现状扫描与评估 | 仅目录结构 + 各文件首 20 行（或标题/摘要） |
| Verifier Agent(s) | 执行一致性校验与有限推测 | 仅目标模块代码/配置 + 对应文档片段 |
| Writer Agent(s) | 具体文档的创建/改写 | 仅目标文档相关的已有内容 + 约束段落 + `_temp/verify-*.md` 与 `_temp/infer-*.md` 结果 |
| Indexer Agent | 创建/维护各层索引文件（`docs/INDEX.md`、`knowledge/INDEX.md`、`knowledge/Instances-INDEX.md`） | 仅对应目录文件列表 + 各文档标题摘要 |
| Auditor Agent | 执行全局更新校验流程 | 按步骤按需加载（见 8.4） |
| Reader Agent（可选） | 代为查阅已有文档并返回摘要 | 仅加载被请求的单篇文档 |

**协作规则：**

- Orchestrator 传递任务时仅含指令+路径，不传文档全文
- 子 Agent 完成后仅返回结果摘要或变更清单，详细校验结果写入 `_temp/verify-*.md`，详细推测结果写入 `_temp/infer-*.md`
- 需引用其他文档时通过 Reader Agent 获取摘要
- 若某子 Agent 需加载的内容预计超过单次上下文窗口的 1/2 或无法一次性读入，按模块/目录进一步拆分任务

#### 构建协作方式二：单 Agent（降级）

**触发条件：** 不支持多 Agent 协作。

- 串行执行，严格渐进式加载
- 每步仅加载当前步骤所需文件
- 若单篇文档超过 500 行或无法一次性读入，分段读取，每段不超过 250 行
- 校验/推测中间结果仍需写入 `_temp/` 目录，保持流程可追溯

**无论哪种构建协作模式，"禁止一次性加载整个规约"是硬性约束。**

### 10.2 操作顺序（仅情况 A/B/C；情况 D 按 2.5 特例路径执行）

**层级标注通则（适用于每个生成/更新的文件）：**

- 约束层/知识层文档：在文档开头加一行层级声明，如 `> 所属层级：约束层（docs/）` 或 `> 所属层级：知识层（knowledge/）`
- 实例文档：按 6.4 元信息区以 `governance: instance` 标注

**Step 1 前置决策：** 完成第 2 章流程（2.1 权限确认 → 2.2 现状扫描 → 2.3 情况判定 → 2.4 保护原则 → 2.5 输出决策报告）；情况 D 走特例路径（见 2.5）。

## 12. 约束力层级与冲突解决

**构建期：** 本提示词（构建期）权威高于其产出的规约体系；执行本提示词期间，任何产出文档与本提示词冲突时，以本提示词为准。

**体系内（建成后）：** `AGENTS.md` ＞ `docs/`（约束层）＞ `knowledge/`（知识层）＞ 实例文档。冲突时上层覆盖下层。

三级约束力标签定义：

| 标签 | 适用层级 | 含义 |
|------|----------|------|
| `[约束]` | 约束层（docs/） | 违反即为执行错误 |
| `[参考]` | 知识层（knowledge/） | Agent 应当遵守；与约束层冲突时以约束层为准 |
| `[自包含指令]` | 实例层 | 文档本身即为完整执行依据 |

冲突处理细则：

- `README.md` 与 `AGENTS.md` 或 `docs/`、`knowledge/` 冲突时，以 `AGENTS.md` 为最终权威，按校验机制修正
- `knowledge/` 层文档与约束层（`docs/`）冲突时，以约束层为准
- `docs/` 同级文档之间冲突时，一律以 `AGENTS.md` 表述为准；`AGENTS.md` 无表述的，冲突双方均标注 `[存在差异]` 并将矛盾对列入汇报等待用户裁定，不得擅自删除任何一方
- 任何文档与项目实际状态冲突时，以实际状态为准（见 2.6.1）
- `README.md` 无约束力，`_temp/` 仅作临时参考，均不参与约束力层级
