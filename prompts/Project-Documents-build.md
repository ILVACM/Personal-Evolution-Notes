# 任务：确保项目知识库文档体系达标（自适应执行）

你的任务是确保本项目仓库具备一套符合下述规范的知识库文档体系。这不意味着必须从零创建——你需要先评估现状，再决定执行路径。最终目标是：无论起点如何，结束时知识库体系必须完全符合本提示词定义的标准。

## 权限与能力确认
执行前请确认你已具备以下能力，若任何一项缺失则立即报告而非静默跳过：
- 文件与目录的读取、创建、写入、修改、删除、移动权限
- 目录树遍历与文件列表获取能力
- 若项目依赖 MCP 服务或特定 Skills（如 Git 操作等），确认其已就绪
- 多 Agent 协作能力检测：检测当前环境是否支持多 Agent 协作（子 Agent 派发 / Worker / Task Delegation 等）

若权限完备，直接开始执行。

## 〇、决策阶段（先决策，再操作）
本任务的执行遵循严格的"先决策再操作"原则。在动手修改任何文件之前，你必须完成以下评估并输出决策报告。

### 0.1 现状扫描
扫描项目根目录及子目录，重点关注：
- 是否已存在 `AGENTS.md`？内容完整度如何？
- 是否已存在 `docs/` 目录？内含哪些文件？是否有索引？
- 是否已存在 `README.md`？内容覆盖度如何？
- 是否存在其他散落的文档（如 `CONTRIBUTING.md`、`wiki/`、`guides/`、零散的 `.md` 文件等）？
- 项目本身的结构、技术栈、规模如何？

### 0.2 执行模式判定
根据扫描结果，判定属于以下哪种情况，并选择对应路径：

| 情况 | 判定标准 | 执行路径 |
| :--- | :--- | :--- |
| A. 从零新建 | 不存在 `AGENTS.md`，不存在 `docs/` 目录，无有效文档体系 | 按规范完整创建 |
| B. 局部补全 | 存在部分文档（如有 `README.md` 但无 `AGENTS.md`，或有零散 `.md` 但无结构化 `docs/`） | 保留已有内容，补建缺失部分，整合散落文档 |
| C. 重构规范化 | 已有一定规模的文档体系，但结构/格式/索引不符合本规范 | 保留核心内容，重组结构，补建索引，统一格式 |
| D. 校验修正 | 已有完整体系且基本符合规范，仅存在小问题 | 仅修正不一致处，不做大改动 |

### 0.3 关键保护原则
无论哪种执行路径，以下规则不可违反：
- ❌ 禁止未经分析直接删除或归档任何已有文档内容
- ❌ 禁止假设已有文档"无用"而跳过不读
- ✅ 已有文档中可用的内容必须保留，可以移动、重组、改写格式，但信息本身不得丢失
- ✅ 若某份已有文档的内容确实与当前项目不符（如过时、错误），应标注 `[已过时-待确认]` 而非直接删除，并在汇报中说明
- ✅ 若需合并多份文档，合并后原文件可删除，但必须确保所有内容已被完整迁移
- ✅ 重构时优先移动和重命名，而非删除后重写

### 0.4 输出决策报告
在动手操作前，向我输出简要决策报告：
```text
📋 [决策报告]
- 现状：简述已有文档情况
- 判定：情况 A / B / C / D
- 执行路径：简述将做什么（保留什么、新建什么、重组什么）
- 协作模式：多 Agent / 单 Agent
- 风险点：（如有）可能的内容冲突或不确定项
```

若判定为情况 D（仅校验修正），报告后直接进入第五节校验流程，无需大动。
若判定为 A / B / C，报告后继续执行后续章节。

## 一、文档真实性校验与自适应推测（核心增量逻辑）

> ⚠️ **本节为强制执行环节**。无论 README 或现有文档看起来多么完整可信，都必须执行一致性校验；无论文档是否缺失，都必须在受限范围内进行自适应推断。此环节是知识库可信度的基石。

### 1.1 文档与实际内容一致性校验
Agent 读取任何文档（README/docs/注释）后，**不得无条件采信**，必须与项目实际产物交叉验证。

- **校验对象**：目录结构、入口文件、配置文件（package.json/pyproject.toml/go.mod 等）、核心代码模块、CI/CD 配置。
- **校验维度**：
    - 技术栈声明 vs 实际依赖清单
    - 目录结构描述 vs 真实文件系统
    - 启动/构建命令 vs Scripts/Makefile/Dockerfile
    - 架构描述 vs 代码模块划分
- **偏差处理**：发现不一致时，以**实际代码/配置为准**，并在输出中明确标注 `[存在差异]`，同时记录差异详情至 `_temp/verify-discrepancies.md`。
- **不可跳过**：即使文档声称“最新”，也必须执行至少一次自动化交叉比对。

### 1.2 文档缺失时的自适应有限推测
当关键信息无文档说明或说明不完整时，允许基于有限线索进行推测，但必须严格遵守以下边界：

- **允许推测的范围**（仅限）：
    - 项目核心功能/用途（What it does）
    - 运行环境与部署目标（Where it runs）
    - 技术栈与框架版本（Tech stack）
- **禁止推测的范围**（红线）：
    - ❌ 业务逻辑细节、算法实现原理
    - ❌ 未来规划、Roadmap
    - ❌ 团队分工、负责人信息
    - ❌ 未经验证的性能指标、安全声明
- **推测依据**：仅可基于目录命名规范、代码注释、依赖清单、配置文件字段、Git 提交信息等**客观痕迹**。
- **标注要求**：所有推测内容必须显式标注 `[推测]` 或 `[推断]`，并注明依据来源（如“基于 package.json dependencies 推断”）。

### 1.3 多 Agent 并行校验与推测执行规范
为应对大仓库上下文过长风险，校验和推测环节**必须**采用多 Agent 并行模式（若环境支持）：

- **任务拆分**：Orchestrator 将校验/推测任务按模块/目录拆分为独立子任务。
- **临时文件机制**：每个子 Agent 将结果写入 `_temp/verify-*.md`（如 `_temp/verify-backend-deps.md`、`_temp/infer-tech-stack.md`），**禁止**直接在内存中返回长文本。
- **汇总机制**：主 Agent 仅读取 `_temp/` 下的结果文件进行汇总，生成最终的可信度分层报告。
- **降级策略**：若不支持多 Agent，则串行执行，但仍需将中间结果写入 `_temp/` 以保持流程一致性和可追溯性。

### 1.4 可信度分层输出标准
在项目背景、技术栈、架构概述等关键输出段落中，**必须**使用以下标签之一作为前缀，便于人工审阅时快速判断复核力度：

| 标签 | 含义 | 人工复核建议 |
| :--- | :--- | :--- |
| `[已校验一致]` | 文档描述与实际代码/配置完全吻合 | 低优先级抽查 |
| `[存在差异]` | 文档与实际不一致，已按实际修正 | **高优先级复核** |
| `[推测]` | 无直接文档，基于客观线索推断 | 中优先级确认 |
| `[推断]` | 基于多处间接证据综合得出 | 中优先级确认 |
| `[待补充]` | 无任何线索，无法推测 | 需人工介入 |

## 二、多 Agent 协作自适应策略

### 模式 A：多 Agent 协作（优先）
- **触发条件**：当前环境支持子 Agent 派发或任务委托机制。
- **核心原则**：每个子 Agent 仅加载完成任务所需的最小上下文，禁止任何 Agent 一次性加载整个知识库。
- **推荐分工架构**（可根据实际协作能力自适应调整）：

| 角色 | 职责 | 加载的上下文 |
| :--- | :--- | :--- |
| Orchestrator（主控） | 任务拆解、分发、汇总、校验调度 | 仅 `AGENTS.md` + 本提示词 + 决策报告 |
| Scanner Agent | 现状扫描与评估 | 仅目录结构 + 各文件首 20 行（或标题/摘要） |
| Verifier Agent(s) <!-- [OPTIMIZED] 新增 --> | 执行一致性校验与有限推测 | 仅目标模块代码/配置 + 对应文档片段 |
| Writer Agent(s) | 具体文档的创建/改写 | 仅目标文档相关的已有内容 + 约束段落 + `_temp/verify-*.md` 结果 |
| Indexer Agent | 创建/维护 `docs/INDEX.md` | 仅 `docs/` 文件列表 + 各文档标题摘要 |
| Auditor Agent | 执行全局更新校验流程 | 按步骤按需加载（见第五节） |
| Reader Agent（可选） | 代为查阅已有文档并返回摘要 | 仅加载被请求的单篇文档 |

- **协作规则**：
    - Orchestrator 传递任务时仅含指令+路径，不传文档全文
    - 子 Agent 完成后仅返回结果摘要或变更清单，**详细校验/推测结果写入 `_temp/verify-*.md`** <!-- [OPTIMIZED] 强化临时文件机制 -->
    - 需引用其他文档时通过 Reader Agent 获取摘要
    - 若某子 Agent 上下文过大，进一步拆分任务

### 模式 B：单 Agent（降级）
- **触发条件**：不支持多 Agent 协作。
- 串行执行，严格渐进式加载
- 每步仅加载当前步骤所需文件
- 若单篇文档过大，分段读取
- **校验/推测中间结果仍需写入 `_temp/` 目录**，保持流程可追溯 <!-- [OPTIMIZED] 补充 -->

无论哪种模式，“禁止一次性加载整个知识库”是硬性约束。

## 三、体系标准（最终状态要求）
无论执行路径如何，最终必须达到以下标准状态：
```text
/
├── AGENTS.md          # 全局权威约束 + 知识库入口（面向 Agent）
├── README.md          # 项目关键信息展示（面向人类）
├── _temp/             # [OPTIMIZED] 新增：校验与推测中间产物目录
│   ├── verify-*.md    # 一致性校验结果
│   └── infer-*.md     # 自适应推测结果
└── docs/              # 知识库内容目录
    ├── INDEX.md       # 索引文档（智能路由入口）
    └── ...            # 具体文档
```

### 各部分职能定位
| 文件/目录 | 面向对象 | 职能 | 约束力 |
| :--- | :--- | :--- | :--- |
| `AGENTS.md` | Agent | 全局最高权威；行为规范、路由方式、协作规范、校验机制 | 最高约束 |
| `docs/INDEX.md` | Agent | 知识库索引与路由；按需跳转，禁止全量加载 | 从属于 `AGENTS.md` |
| `docs/*.md` | Agent | 具体知识内容 | 从属于 `AGENTS.md` |
| `README.md` | 人类 | 项目关键信息纯展示窗口，无约束职能 | 无约束力 |
| `_temp/*.md` | Agent/人类 | 校验与推测过程产物，供审计追溯，非正式知识 | 临时参考 | <!-- [OPTIMIZED] 新增 -->

冲突处理：`README.md` 与 `AGENTS.md` 或 `docs/` 冲突时，以 `AGENTS.md` 为最终权威，按校验机制修正。

## 四、各文件内容与格式要求

### 4.1 `AGENTS.md`
必须包含以下板块：
- **全局行为约束**：Agent 通用规则；声明本文件为最高权威
- **知识库路由指引**：
    - 明确索引路径：`docs/INDEX.md`
    - 标准流程：`AGENTS.md → docs/INDEX.md → 目标文档`
    - 渐进式加载，禁止全量读取
- **多 Agent 协作规范**：
    - 本项目支持多 Agent 协作
    - 最小上下文原则
    - 任务传递仅含指令+路径
    - 子 Agent 仅返回摘要，**校验/推测结果写入 `_temp/`** <!-- [OPTIMIZED] 补充 -->
- **全局更新校验机制**（完整写入，见第五节）
- **文档变更操作规范**：任何变更后必须执行全局校验
- **可信度标签使用说明**：<!-- [OPTIMIZED] 新增 -->
    - 列出所有可用标签及其含义
    - 要求在关键输出中强制使用

### 4.2 `docs/INDEX.md`
- 文档清单表，每条含：文件路径、标题、一句话摘要、标签/分类、最后更新日期、**可信度状态** <!-- [OPTIMIZED] 新增字段 -->
- 路由说明：Agent 如何按关键词/主题定位目标文档
- 维护规则：文件增删改时同步更新索引，一一对应无遗漏

### 4.3 `docs/` 目录
- 根据项目现状组织具体文档（架构说明、开发规范、环境配置等）
- 每篇开头含：标题、适用范围、最后更新时间、**可信度标签** <!-- [OPTIMIZED] 新增 -->
- 文档间引用用相对路径
- 已有文档应被合理归入此目录（移动/重命名），而非丢弃

### 4.4 `README.md`
- 纯展示，无约束条款
- 内容：项目简介、核心特性、技术栈、快速开始提示、项目结构概览
- **关键信息旁标注可信度标签**（如 `技术栈：Python 3.11 + FastAPI [已校验一致]`） <!-- [OPTIMIZED] 新增 -->
- 精简可读，30 秒抓住要点
- 末尾附注：`> 本文件由知识库体系自动维护，详细信息请参阅 docs/ 目录。`

## 五、全局更新校验机制（必须完整写入 AGENTS.md）
触发条件：任何文档变更完成后（新建、删除、修改、移动、重命名），无论之前是否校验过、无论提示词是否要求，必须执行以下三步。
多 Agent 模式下：由 Orchestrator 调度 Auditor Agent 分步执行，每步仅加载该步所需文件，禁止合并。

### Step 1 — AGENTS.md 自洽性审计
- 仅加载 `AGENTS.md`
- 检查：逻辑自洽、路由路径正确、校验机制完整、各板块无矛盾、**可信度标签使用规范** <!-- [OPTIMIZED] 补充 -->
- 有问题则修正后重新审计

### Step 2 — 索引与文件一致性校验
- 仅加载 `docs/INDEX.md` + `docs/` 目录文件列表
- 比对：无幽灵条目、无遗漏、标签/摘要与实际匹配、**可信度状态字段已填写** <!-- [OPTIMIZED] 补充 -->
- 不一致则修正

### Step 3 — README.md 同步更新
- 仅加载 `README.md` + 相关文档摘要（不读全文）
- 确保信息准确、无约束条款、**关键信息带可信度标签** <!-- [OPTIMIZED] 补充 -->
- 有变化则更新

### 校验完成确认

```text
✅ [校验通过]

- docs/INDEX.md：N 篇文档，索引与实际文件一一对应，可信度状态已填写

- 执行路径：新建 / 局部补全 / 重构规范化 / 校验修正
```

6.  **最终校验**：操作完成后立即执行一次完整全局校验
7.  **输出汇报**：

    - 校验报告

    - （若有）标注为 `[存在差异]` / `[推测]` / `[推断]` 的内容清单及依据 <!-- [OPTIMIZED] 新增 -->
